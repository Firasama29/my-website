How My Portfolio Was Built

A complete walkthrough of every file, library, and concept — written for a Java/Spring Boot developer.

1. Overview

The portfolio is a statically generated website. That means at build time, every page is pre-rendered into plain HTML files. When someone visits the site, the server just sends those HTML files — there's no database query, no running server process per request.

Java analogy: Think of it like pre-computing every possible API response and storing the results in files. Instead of your Spring Boot app computing a response on every request, the responses are already computed and served as files. Blazing fast and cheap to host.

The site has four sections and two types of pages:

📄 Single-page sections

  • Hero / About
  • Skills
  • Contact

All live on the / homepage.

📰 Blog (dynamic routes)

  • /blog — article listing
  • /blog/guide-to-npe — individual article
  • 23 articles total, all pre-rendered

4. How Next.js Works (File-Based Routing)

In Spring Boot, you annotate a method with @GetMapping("/blog") to handle a route. In Next.js, the file path IS the route. No annotations needed.

File pathURL it handles
app/page.tsx/
app/blog/page.tsx/blog
app/blog/[slug]/page.tsx/blog/anything-here

The [slug] in the folder name is a dynamic segment — like a path variable in Spring Boot. When someone visits /blog/guide-to-npe, the value "guide-to-npe" is passed into the page as a parameter called slug.

Java analogy: 
// Spring Boot
@GetMapping("/blog/{slug}")
public String blogPost(@PathVariable String slug) { ... }

// Next.js equivalent — just the file path:
// app/blog/[slug]/page.tsx
// The slug is available via: const { slug } = await props.params

Server Components (the default)

All components in the app/ directory are Server Components by default. They run on the server (or at build time), have access to the filesystem, and send plain HTML to the browser. No JavaScript bundle shipped to the user for these.

If you need interactivity (click handlers, state), you add "use client" at the top — we didn't need that in this project since everything is static.

What is JSX? That HTML-looking syntax inside JavaScript is called JSX. It's not real HTML — it's a syntax extension that React compiles to JavaScript function calls. <Hero /> is equivalent to calling Hero() and getting back UI markup.

7. Components

A component is just a TypeScript function that returns JSX (markup). Each component lives in its own file in components/.

Java analogy: Think of each component as a small class with one job — render a piece of UI. Like a @Component but instead of containing business logic, it contains UI markup.

Navbar.tsx

The sticky top navigation bar. Uses Next.js <Link> for navigation — like an <a> tag but with client-side routing (no full page reload).

Hero.tsx

The big intro section with name, title, bio, and CTA buttons. Pure static markup — no logic.

Skills.tsx

Defines a skills array (data) and maps over it to render cards. The .map() is like a Java stream — it transforms each item into a UI element.

BlogCard.tsx

Receives props (slug, title, date, excerpt, tags) and renders one article card. Props are like constructor parameters — data passed in from outside.

Contact.tsx

Email and GitHub links rendered as styled cards. Static markup.

9. lib/posts.ts — The Data Layer

This file is the "repository" of the blog. It reads files from disk and returns structured data. It has three exported functions:

import fs from 'fs';          // Node.js built-in: read files from disk
import path from 'path';      // Node.js built-in: build file paths safely
import matter from 'gray-matter';   // Parse YAML frontmatter
import { remark } from 'remark';    // Markdown processor
import remarkGfm from 'remark-gfm';   // GitHub Flavored Markdown plugin
import remarkHtml from 'remark-html';  // Converts Markdown → HTML

// Points to the content/posts/ folder
const postsDir = path.join(process.cwd(), 'content/posts');

// ① Returns ALL posts sorted by date (newest first)
//    Used by: app/blog/page.tsx (the listing page)
export function getAllPosts(): PostMeta[] {
  const files = fs.readdirSync(postsDir).filter(f => f.endsWith('.md'));

  return files
    .map(filename => {
      const raw = fs.readFileSync(path.join(postsDir, filename), 'utf8');
      const { data } = matter(raw); // data = the frontmatter object
      return { slug: filename.replace(/\.md$/, ''), ...data };
    })
    .sort((a, b) => a.date < b.date ? 1 : -1); // newest first
}

// ② Returns ONE post's full content as HTML
//    Used by: app/blog/[slug]/page.tsx
export async function getPostBySlug(slug: string): Promise<Post | null> {
  const raw = fs.readFileSync(`${postsDir}/${slug}.md`, 'utf8');
  const { data, content } = matter(raw); // data = frontmatter, content = body text

  // Convert Markdown body to HTML string
  const processed = await remark()
    .use(remarkGfm)   // enable tables, strikethrough, etc.
    .use(remarkHtml)  // output HTML
    .process(content);

  return { ...data, slug, contentHtml: processed.toString() };
}

// ③ Returns all slugs — used by generateStaticParams to pre-render all posts
export function getAllSlugs(): string[] {
  return fs.readdirSync(postsDir)
    .filter(f => f.endsWith('.md'))
    .map(f => f.replace(/\.md$/, ''));
}
Java analogy: getAllPosts() is like a @Repository method that does findAll(). getPostBySlug() is like findById(). Except instead of a database, the "database" is a folder of Markdown files on disk.

10. Blog Pages

app/blog/page.tsx — The Listing Page

import { getAllPosts } from "@/lib/posts";
import BlogCard from "@/components/BlogCard";

export default function BlogPage() {
  const posts = getAllPosts();  // reads all 23 markdown files

  return (
    <div>
      {posts.map(post => (
        {/* For each post, render a BlogCard */}
        <BlogCard key={post.slug} {...post} />
      ))}
    </div>
  );
}

{...post} is the spread operator — it passes all properties of the post object as individual props to BlogCard. Like calling a method with all fields of an object unpacked as separate arguments.

app/blog/[slug]/page.tsx — Individual Article Page

// This tells Next.js: "at build time, pre-render one page for EACH slug"
export async function generateStaticParams() {
  return getAllSlugs().map(slug => ({ slug }));
  // Returns: [{ slug: "guide-to-npe" }, { slug: "string-pool" }, ...]
}

// props.params.slug = the value from the URL (e.g. "guide-to-npe")
export default async function BlogPostPage(props: PageProps<'/blog/[slug]'>) {
  const { slug } = await props.params;   // params is a Promise in Next.js 15
  const post = await getPostBySlug(slug); // read + parse the markdown file

  return (
    <article
      className="prose prose-slate prose-lg"  {/* Tailwind typography classes */}
      dangerouslySetInnerHTML={{ __html: post.contentHtml }}  {/* inject HTML */}
    />
  );
}
generateStaticParams is key to SSG. It tells Next.js which slugs exist, so it can pre-render a page for each one at build time — no server needed at runtime.

11. Styling — Tailwind CSS

Tailwind is a utility-first CSS framework. Instead of writing CSS files, you apply small, single-purpose classes directly in your JSX.

Tailwind classWhat it does
bg-whitebackground-color: white
text-slate-800color: dark slate
px-6padding-left + padding-right: 24px
py-20padding-top + padding-bottom: 80px
flex items-center gap-6display: flex; align-items: center; gap: 24px
hover:text-blue-600on hover: color changes to blue-600
sm:grid-cols-2on small screens+: 2 columns (responsive)
prose prose-slate@tailwindcss/typography: styles rendered Markdown

The prose class (from the @tailwindcss/typography plugin) automatically styles whatever HTML is inside — headings, paragraphs, code blocks, lists. That's what makes blog articles look good without writing any custom CSS.

12. Config Files

tailwind.config.ts

Tells Tailwind where your component files are so it can scan them and only include the CSS classes you actually use (tree-shaking).

content: [
  "./app/**/*.{js,ts,jsx,tsx}",       // scan app/ folder
  "./components/**/*.{js,ts,jsx,tsx}", // scan components/ folder
],
plugins: [typography],  // enable the prose/typography plugin

next.config.ts

Next.js project configuration. We set outputFileTracingRoot to avoid a warning about multiple lockfiles detected in parent directories.

postcss.config.mjs

PostCSS is a CSS processing pipeline. Tailwind uses it to transform your CSS. Without this, Tailwind's utility classes wouldn't be generated.

plugins: {
  tailwindcss: {},   // generate Tailwind utilities
  autoprefixer: {},  // add vendor prefixes (-webkit-, etc.) for browser compat
}

tsconfig.json

TypeScript compiler settings. The important bit is the @ alias — it lets you write @/components/Navbar instead of ../../components/Navbar.

"paths": { "@/*": ["./*"] }  // @ = project root

13. Deployment (Netlify)

The netlify.toml file tells Netlify how to build and deploy the site:

[build]
  command = "npm run build"  # runs: next build → generates static HTML files
  publish = ".next"          # the folder Netlify serves

[[plugins]]
  package = "@netlify/plugin-nextjs"  # Netlify-specific Next.js adapter

When you connect the GitHub repo to Netlify, every push to main triggers a new build. Netlify runs npm run build, which pre-renders all 29 pages, then serves them as static files globally via CDN.

14. Full Data Flow at Build Time

Here's exactly what happens when you run npm run build:

Step 1 — Next.js scans the app/ directory

It finds: page.tsx, blog/page.tsx, blog/[slug]/page.tsx.

Step 2 — For dynamic routes, it calls generateStaticParams()

getAllSlugs() reads content/posts/ → returns 23 slugs. Next.js now knows it needs to build 23 blog post pages.

Step 3 — For each slug, it renders the page

getPostBySlug("guide-to-npe") is called → reads content/posts/guide-to-npe.md → parses frontmatter with gray-matter → converts Markdown body to HTML with remark → returns the data.

Step 4 — The page component renders to HTML

The BlogPostPage component receives the post data and renders it as HTML. Tailwind's prose styles are applied.

Step 5 — Output: 29 static HTML files

1 homepage + 1 blog listing + 23 blog posts + 4 others = 29 pages. All saved in .next/. The site is ready to serve with zero server-side processing per request.

Summary: At build time everything runs on Node.js (server-side). In production, users just receive pre-built HTML + CSS + minimal JS. No Java process, no database, no server per request.
